# Целесообразный выбор модели

Политика проекта, дата проверки возможностей: 2026-09-17.
Выбирать по результату задачи с учётом исправлений, задержки и расхода,
а не по принципу «самая дорогая всегда лучше» или «самая дешёвая экономнее».

## Что действительно доступно

Перед запуском проверить актуальный список и ограничения инструмента.
При создании этих инструкций spawn_agent объявлял:

| ID | Исходный кандидат для оценки в этом проекте |
|---|---|
| gpt-5.6-luna | Узкий поиск, простые повторяемые правки и проверки |
| gpt-5.6-terra | Ограниченные Kotlin-задачи с ясными контрактами |
| gpt-5.6-sol | Многошаговая реализация и интеграция |
| gpt-6-astra | Неясная причина, сложные гонки/focus/lifecycle, критическое ревью |
| gpt-5.5 | Существующий проверенный процесс или сравнение с базовой моделью |

Это наши стартовые гипотезы, а не измеренный рейтинг Bobyl TV.
Список из живого инструмента имеет приоритет над этим снимком.
Не подменять ID похожим названием из API-документации.

По умолчанию оставлять модель родителя. Если инструмент разрешает override
только по явному запросу пользователя, соблюдать это. Без такого запроса указать
рекомендацию и фактическую унаследованную модель, продолжить доступной моделью.
Не утверждать, что Markdown или значение в шаблоне изменило модель/effort.

## Оценка до задачи

Зафиксировать четыре оценки по 0–2:

- Неопределённость: известное решение / нужно исследование / причина неизвестна.
- Связность: один участок / несколько контрактов / сквозное поведение.
- Риск: документация / обычная логика / auth, данные, concurrency, playback.
- Проверяемость: быстрый надёжный тест / частичное покрытие / только сложный TV-сценарий.

Сумма — эвристика проекта, не прогноз качества:

| Сумма | Кандидат | Effort |
|---|---|---|
| 0–2 | Luna или текущая модель | low / medium |
| 3–5 | Terra или Sol | medium |
| 6–8 | Astra или наиболее подходящая доступная | high |

Для потенциальной потери данных/авторизации или гонок нужен сильный независимый
review независимо от суммы. Максимальные уровни не использовать автоматически.
Проверять, что выбранная модель поддерживает effort; если управлять им нельзя,
фиксировать «унаследован» вместо выдуманного значения.

Примеры: исправление Markdown-ссылки — один агент, low; парсер с fixtures —
Terra/medium; редкая потеря focus при pagination и быстром D-pad —
Astra/high как кандидат; рутинная установка готового APK не требует сильной модели.

## Оценка после задачи

В [RUN](templates/RUN.md) фиксировать только факты:

- Модель и effort: запрошенные / фактические / неизвестные.
- Время до принятого результата, число возвратов на доработку.
- Результаты тестов, подтверждённые дефекты на ревью, ручные исправления.
- Токены/стоимость — только если среда их предоставляет. Иначе «нет данных».
- Вывод: оставить / понизить на следующей аналогичной задаче / повысить /
  сначала исправить постановку или среду.

При API-расчёте учитывать input, cached input и output раздельно по проверенным
тарифам. Не выдавать тариф API за стоимость подписки Codex и не вычислять расход
конкретного субагента из изменения общей квоты аккаунта.

Повышение оправдано повторной ошибкой рассуждения после уточнения контракта,
пропущенными краевыми случаями или сложностью проверки. Понижение пробовать на
следующей малорисковой похожей задаче, когда результаты уже устойчивы.
Один успех/неуспех недостаточен для рейтинга; сравнивать несколько сопоставимых
задач с одинаковыми критериями, учитывать сложность и ручную доработку.
Не тратить дополнительные прогоны на сравнительный benchmark без задачи пользователя.
