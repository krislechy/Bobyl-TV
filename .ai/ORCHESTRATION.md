# Оркестрация

## 1. Определить задачу

Оркестратор фиксирует результат, критерии приёмки, границы запроса, текущий HEAD,
незакоммиченные изменения и минимальную проверку. Диагностика заканчивается
выводом о причине; исправление выполняется, если оно входит в запрос.

Сначала определить действие на критическом пути, которое оркестратор сделает сам.
Разделять работу только при наличии независимых результатов. Для простой правки
достаточно одной роли в текущем агенте. Для сложной задачи начальный предел —
два параллельных исполнителя; расширять до трёх только при непересекающейся работе
и понятной пользе. Это локальная рекомендация, не лимит Codex.

## 2. Выдать контракт

Каждому исполнителю передать [TASK](templates/TASK.md):

- Цель, критерии, исходное состояние и нужные файлы.
- Точную роль, абсолютный repo_root, tools_root и режим среды.
- Разрешённые изменения: точные пути; при отсутствии write set — только чтение.
- Фиксированный контракт DTO/UiState/сигнатур, если есть зависимости.
- Зависимости, ограничения и формат результата.
- При выборе модели — фактическую и рекомендуемую модель/effort по [MODELS](MODELS.md);
  иначе сохранить настройки текущего агента.

Нельзя назначить UI-агенту «весь UI», а playback-агенту одновременно PlaybackDialog.
Ролевая карта — подсказка, не блокировка файлов. Общие файлы резервирует оркестратор.
Резервирование фиксируется в одном плане, который редактирует только он.
При одной задаче план можно держать в разговоре; для долгой работы использовать
[шаблон RUN](templates/RUN.md) в отдельном файле задачи без секретов.

## 3. Выбрать среду

**Общий checkout:** только непересекающиеся write sets. Агенты не запускают
сборку во время чужих правок, не меняют ветку, индекс или чужой diff.
Параллельное чтение разрешено; вывод ревью относится к зафиксированному состоянию.

**Изолированный checkout/worktree:** у каждого исполнителя своё дерево.
Проверить реальные свойства инструмента; fork истории не доказывает изоляцию файлов.
Не предполагать, что untracked файлы и текущий dirty diff попали в worktree.
Нужные новые инструкции и исходный diff передать явно. `local.properties` и SDK
настроить локально по tools_root; не копировать секреты и настройки подписи без причины.
Интеграцию выполняет оркестратор через проверенный diff/механизм среды.
Нельзя считать завершение субагента автоматическим объединением изменений.

**Отдельные независимые задачи:** использовать готовую карточку с теми же правилами.
Новые пользовательские задачи создавать только по явному запросу пользователя.
Обычный субагент не требует создания отдельной задачи через create_thread.
Планы разных задач не являются общим mutex: перед Gradle/ADB каждый владелец
обязан получить один OS file lock `tools_root/locks/bobyl-build-device.lock`
по протоколу build-verifier. Если ресурс занят, продолжать независимую работу
или сообщить ожидание; не удалять lock-файл и не обходить его отдельным процессом.

## 4. Использовать субагентов

- Найти фактически доступный инструмент запуска субагента и прочитать его схему.
- Не считать названия инструментов из прошлых сессий доказательством доступности.
  Проверить фактические инструменты запуска, передачи задания, ожидания и завершения.
- Передавать минимальный достаточный контекст. Указывать ссылки и ключевые решения,
  а не всю историю по умолчанию.
- Независимую побочную работу делегировать, локально продолжать критический путь.
- По умолчанию наследовать модель родителя. Ограничения инструмента на override
  важнее рекомендательной таблицы; «оценить модель» не означает «сменить модель».
- Исполнитель не порождает новых агентов самостоятельно: возвращает запрос
  оркестратору. Один уровень делегирования по умолчанию.
- Не выполнять параллельно ту же самую подзадачу. Независимое ревью имеет другую цель:
  проверить результат и риски, а не заново реализовать решение.
- Ожидать результат, когда он нужен для следующего шага; не опрашивать статус без причины.
- При отсутствии инструментов выполнить роли последовательно и прямо указать это.
- По завершении принять результат, интегрировать при необходимости, закрыть субагента.

## 5. Разрешать зависимости и конфликты

Если нужны изменения вне write set, исполнитель останавливает только зависимую часть
и сообщает владельцу точный файл, нужную сигнатуру и причину.
Оркестратор изменяет контракт и уведомляет зависимых исполнителей, либо делает правку сам.
Нельзя молча расширять область записи или перетирать чужие изменения.

При ошибке сначала проверить воспроизведение, входные данные и среду.
Одна корректировка задания при недопонимании; при повторной содержательной неудаче
пересмотреть декомпозицию/effort/модель. Недоступная сеть, SDK или приставка
не исправляются повышением модели. Никаких бесконечных повторов.

## 6. Интегрировать и проверить

1. Получить список изменённых файлов, diff и отчёт каждого исполнителя.
2. Сверить write set, исходное состояние, контракты и незапрошенные изменения.
3. Для рискованных изменений запросить независимое [ревью](roles/reviewer.md).
4. Остановить записи в проверяемое дерево. Передать единое владение Gradle/ADB
   [build-verifier](roles/build-verifier.md). Не запускать несколько debug-сборок
   в разных worktree: каждая успешная сборка требует установки на одну приставку.
5. Выполнить проверки по риску, после успешного debug немедленно установить Dev с -r.
6. Исправления после проверки отменяют только затронутые результаты: повторить нужные
   проверки. Не повторять всё при неизменном коде без причины.
7. Завершить: выполнено, проверки, ограничения, оставшиеся действия; оценка модели — только если проводилась.
   Отсутствие проверки на TV отметить отдельно. Обоснованный блокер не выдавать за успех.
